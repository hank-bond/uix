# Backlog

Each entry records the trigger, constraints, and likely scope so a reader does not need to reconstruct the discussion. Convention evaluations track open questions, and migrations track adoption of approved rules. Promote a deliverable to its own plan when its execution details no longer fit in one entry.

## Convention evaluations

Convention evaluations track open vocabulary and rule questions. They do not authorize conventions or migrations.

### Transport boundary role

- **Status:** Unscheduled. No naming decision or migration is approved.
- **Trigger:** Comparing the `AttachmentWebBindingTransport` and `AttachmentWebRootsObservable` interfaces revealed an unclear distinction. Both provide snapshots and subscriptions, but those operations alone do not explain the naming roles.
- **Candidate meaning:** A communication capability connecting two sides across a host boundary without requiring callers to know the delivery mechanism. This sketch remains unclear and needs more thought, especially about what constitutes the boundary and which behaviors the capability provides.
- **Intent:** Use consistent names for communication boundaries across inter-process communication (IPC), WebSocket, and Hypertext Transfer Protocol (HTTP). Distinguish the capability from the payload bytes without restricting the term to IPC and WebSocket.
- **Comparison:** The observable guidance in [`naming.md`](../docs/architecture/conventions/naming.md#observable-capabilities) specifies synchronous access to a stable, immutable current snapshot and change notifications. It does not require a separate state owner or wrapper. The roots observable implementation manages bootstrap, revision ordering, and cleanup, but the suffix alone does not imply those responsibilities.
- **Evaluation:** Distinguish the boundary capability from delivery mechanisms, adapters, handler registries, and local snapshot observables. Audit the `AttachmentWebBindingTransport` and `ChannelTransport` interfaces, the `WorkspaceResourceTransport` and `ElectronResourceTransport` classes, and the `ContentTransportRegistrar` type. These names describe different abstraction levels. Evaluate their responsibilities rather than treating existing names as precedent. Decide the convention before tracking any approved migration.

## Convention migrations

Select these migrations independently between plans. Start each migration with an audit of every use within the convention's repository scope, including previously changed code. The examples identify places to start, not a complete inventory. Remove an entry only after the migration lands.

### Turn and run vocabulary

- **Convention:** [`prose-terms.md`](../docs/architecture/conventions/lexicon/prose-terms.md). `run` names one complete user-prompt-to-agent-response exchange. `turn` names one model response plus its tool executions within a run.
- **Status:** Unscheduled beyond the initial slice.
- **Initial change:** The reviewed specifications use `Agent turn` for one model response plus its tool executions and `Agent run` for the complete prompt exchange. [`feature-turn-state.md`](../docs/specs/feature-turn-state.md) defines capture boundaries. [`agent-instances.md`](../docs/specs/agent-instances.md) and [`connection-agent-attachments.md`](../docs/specs/connection-agent-attachments.md) protect complete runs. [`workspace-file-state.md`](../docs/specs/workspace-file-state.md) applies pre-run and post-turn capture. These align with Pi's `turn_start` and `turn_end` events within `agent_start` and `agent_end`.
- **Scope:** Audit active docs, comments, and identifiers that previously used `turn` for one user-agent exchange or `run` informally as a verb. Check transcripts, turn-state code paths, and existing migration entries.

### Capability lifetime scope

- **Convention:** [`state-and-capabilities.md`](../docs/architecture/conventions/state-and-capabilities.md#central-ownership-capability-handles). Lazy lookup preserves a capability's declared scope. It does not grant authority over a replacement generation implicitly.
- **Status:** Repository-wide audit unscheduled.
- **Initial change:** The composition and attachment specifications distinguish accepted request authority from the replacement authority obtained after page reload.
- **Scope:** Audit guidance and capabilities that assume every handle survives replacement. Preserve stable-owner capabilities where their scope permits replacement, and preserve exact-generation authority for guards and bound clients.

### Guard naming forms

- **Convention:** [`Guard`](../docs/architecture/conventions/lexicon/code-terms.md#uix-owned-role-terms) and [guard naming](../docs/architecture/conventions/lifetimes.md#guard-naming). `ThingGuard` prevents disposal of the named thing. `ActionGuard` prevents the named action from starting.
- **Status:** Repository-wide audit unscheduled.
- **Initial change:** The R1 fixes in [`viewpoint-canvas-document-route.md`](./archive/viewpoint-canvas-document-route.md) renamed the turn and handler acquisition to `acquireReloadGuard()` and its local holders to `_reloadGuard`. `WorkspaceRuntime` now owns both that acquisition and reload invocation, following [`lifetimes.guard-authority`](../docs/architecture/conventions/rules/lifetimes.guard-authority.md). The separate `ReloadAdmission` class and reload coordinator are deleted. The operation tracker remains the separate owner of cancellation and completion.
- **Scope:** Audit guard names, acquisition methods, and descriptions across active code and documentation. Check that each owner of a guarded action also owns guard creation, tracking, and enforcement. Holder-role names such as `operationGuard` are starting points for review, not automatic renames. Preserve the supervised-object specialization `Guard<Value>` and historical decisions. Do not introduce operation permits as a synonym for reload guards.

### Host-role naming

- **Convention:** [`naming.host-role`](../docs/architecture/conventions/rules/naming.host-role.md).
- **Status:** Unscheduled.
- **Initial change:** The W7 slice in [`viewpoint-canvas-document-route.md`](./archive/viewpoint-canvas-document-route.md) removed redundant host prefixes from the binding state, roots observable, and address encoder and decoder. For example, it renamed the `ElectronAttachmentWebBindingState` class to `AttachmentWebBindingState` in [`attachment-web-binding-state.ts`](../hosts/electron/src/main/attachment-web-binding-state.ts).
- **Signals:** Resource transports, workspace clients, action sources, and launcher adapters across both hosts have names worth reviewing.

### Branded constrained strings

- **Convention:** [`module-boundaries.branded-strings`](../docs/architecture/conventions/rules/module-boundaries.branded-strings.md).
- **Status:** Unscheduled.
- **Initial change:** The W7 slice added the `FeatureWebRootUrl` type and its validator in [`feature-web-root-url.ts`](../packages/api/src/feature-web-root-url.ts). The host encoder returns a branded value, and the roots observable, surface provider, and route client preserve its type. Reviewing the encoder in [`viewpoint-urls.ts`](../hosts/electron/src/viewpoint-urls.ts) prompted the convention.
- **Signals:** Other identifiers, keys, and formatted addresses across the repository.
- **Context:** The feature-root type is host-neutral, while each host owns its scheme and physical encoding. This division does not require changing the `ResourceProtocolScheme` constant or its role in shared logical resource addresses.

## Deliverables

Promote a seed to its own plan once ordered units, acceptance criteria, or design rationale no longer fit comfortably here. Delete the seed when it graduates.

- **Workspace development baseline adoption:** unscheduled. Apply [`workspace-development-baseline.md`](../docs/specs/workspace-development-baseline.md) first to the `uix-workspaces` repository, using shared tooling with repository-specific content and configuration. Keep Recall's history import, analysis, and browsing work separate. This adoption needs no provisioning wizard, per-Agent worktrees, or sandboxing. Move these rollout details into a dedicated plan when implementation units are selected.
- **Agent composition replacement:** unscheduled. Implement [`feature-composition.md`](../docs/specs/feature-composition.md) without partial feature acceptance or browser hot replacement. Planning must settle transitive module refresh, provisional restoration without durable mutation, and ordering against settings persistence. Include full page reload and attachment-authority revocation in the same reviewed path. Do not prescribe transport tokens or module-loader mechanics in the specification.
- **Browser presentation state:** unscheduled. Implement [`browser-presentation-state.md`](../docs/specs/browser-presentation-state.md) through shared opt-in helpers backed by browser-local storage. Migrate Chat summary preferences out of manifest settings and persist tool-block expansion by durable item identity. Remove the old manifest-backed presentation path rather than retaining two authorities. Preserve author defaults and usable interaction when storage is unavailable or values are incompatible.
- **Nested workspaces through sparse checkout:** deferred. [`workspace-file-state.md`](../docs/specs/workspace-file-state.md) initially requires the workspace directory to be a Git worktree root. Keep workspace-relative source and dependency resolution conceptually separate from Git administration. Later sparse checkout can populate a nested workspace subtree without copying its enclosing monorepo. Do not add sparse-checkout machinery or a generic provisioning abstraction to the initial implementation. Before promotion, settle workspace-to-repository path mapping, sparse patterns, checkpoint handling of omitted paths, and dependencies outside the workspace subtree.

- **Coordinated Agent reload:** deferred beyond the minimum viable product. [`feature-composition.md`](../docs/specs/feature-composition.md) initially supports selected-Agent reload only. Before adding reload-all, settle which Agents participate, busy handling, per-Agent reporting, and whether inactive sessions remain unstarted. Reloading Agents from their own worktrees does not synchronize their source versions.
- **Queued Agent reloads:** deferred unless immediate busy rejection becomes a usability problem. [`feature-composition.md`](../docs/specs/feature-composition.md) initially rejects reload during an active run or contribution handler and does not queue a retry. Before adding a queue, settle cancellation, duplicate requests, target lifetime, and how completion or failure reaches the requester.
- **Agent-assisted manifest conflict resolution:** deferred. [`feature-composition.md`](../docs/specs/feature-composition.md) uses last-write-wins for manifest writes, including application writes that overwrite pending Agent edits. Consider later conflict detection and Agent-assisted resolution as part of the broader recovery work. Do not add a configuration concurrency system to initial composition loading. Settle detection, recovery context, and user control before implementation.
- **Surface contributions + workspace layout**: done. Features export `defineSurface` contributions from their workspace dirs. `surface-host.tsx` composes the flat list, and `SurfaceMount` hands each surface its typed channel client.
- **Typed channel events**: done: shared `ChannelContract`s drive backend handlers (`withHandlers`), typed frontend clients (`createChannelClient`), and typed event publishers (`FeatureEventPublisherFactory`). Events are schema-validated on both publish and subscribe.
- **Iframe surface transport**, the containment mode for foreign/generated/executable surface code (shelved when the Host/Workspace iframe collapsed, see [workspace-runtime-foundation](./archive/workspace-runtime-foundation.md)). Everything in [runtime-surface-composition](./archive/runtime-surface-composition.md) is trusted first-party page-realm code, so this waits for the first untrusted surface. Related: feature-agent link metadata on surfaces, later.
- **`uix-core` embedded-Pi config**: orientation block + doc map + smoke-test tools injected into the host's agent.
- **Agent tool contributions from features**: done: manifest features register Pi tools into the owned session via `AgentToolRegistry`.
- **Public feature channel contracts**: establish the convention/mechanism for a feature to expose a stable typed API other features can deliberately depend on. For example, a calendar feature publishes `calendarChannels` (requests + events) as its public contract. Sibling features/surfaces can import that contract without reaching through ad hoc source paths. Mechanics exist in the channel substrate. Missing piece is packaging/discovery/import ergonomics and the rule for what counts as a feature's public API.
- **Replaceable cross-feature settings editor**: apply the command-palette pattern to settings. Normal `ctx.settings` / `useFeatureSetting` handles stay owner-scoped. The substrate exposes an intentional cross-feature editor axis: serializable setting descriptors, complete scope values/defaults, structural and referential diagnostics, draft validation, and constrained whole-scope candidate replacement. It replaces other features' raw handles. An ordinary ambient feature renders the shipped modal and remains removable/replaceable. Each feature may still build a richer scoped editor for its own domain. The first referential case is `settings.keybindings`. Its dynamically validated action-id map must retain well-formed inactive ids but include them in an unresolved projection. The human can then correct/delete typos or keep dormant bindings. Until this is promoted, humans and agents edit `uix.workspace.json` and reload. Before implementation, settle descriptor presentation metadata and treatment of secret/non-editable settings. Also settle malformed external-edit recovery and whether custom setting controls are links/actions into feature-owned UI rather than generic schema widgets.
- **Sharpen `@uix/api` import boundaries**: fast follow after the settings API naming cleanup. The root `@uix/api` barrel is fuzzy: it behaves like a backend/feature-entry convenience barrel, while renderer-facing APIs live under `@uix/api/workspace` because they import React. Make the semantic import paths explicit. Prefer focused submodules (`@uix/api/feature`, `@uix/api/settings`, `@uix/api/channels`, `@uix/api/workspace`). Either shrink/remove the root barrel or define it as a deliberately tiny React-free shared surface. Avoid adding `@uix/api/backend` unless `feature` proves too narrow.
- **Tracked document publication + external edit absorption**: grow the document store/buffer model so the feature can publish a document to a visible workspace path. The agent, user, bash tools, or external apps can edit that path. UIX watches only tracked published paths, not arbitrary globs. External writes import into the document store as new current versions/snapshots, publish channel updates to surfaces, and record version refs through turn-state for branch rollback. The eventual git-backed document store provides snapshot compression/diffing/history. The filesystem path is just the local publication surface. Hydration should be able to compare tracked published files against the latest known version. It imports changed disk content on demand/startup. Correctness then does not rely solely on watcher delivery. Its mutation/effect boundary is tracked in [rollback boundaries](../docs/design/rollback-boundaries.md). The workspace-file half of this seed is superseded for git workspaces by session worktrees plus the host watcher (see [session worktrees and turn checkpoints](../docs/decisions/2026-08-08-session-worktrees-and-turn-checkpoints.md)). The remaining value is publication for managed, `doc://`-addressed content.
- **File editor MVP**: the first product vertical: a Monaco source-editing surface opened by clicking file names in Chat. Chat owns the link presentation and calls an editor channel contract directly (the pattern Canvas already uses to call `agent.requests.prompt`). No viewer catalog yet. The editor is a feature surface over git-backed session worktree files, with the anchored buffer and `changed` events mirroring Canvas. See [cross-feature interoperability](../docs/design/cross-feature-interoperability.md) and [anchored base tools](../docs/decisions/2026-08-08-anchored-base-tools.md). Monaco integration flags: workers against the `uix-resource://` surface origin and CSS that must be vendored or shared (surface styles cannot escape the feature root).
- **Mutable agent cwd rebind**: implement the accepted [project-root vs agent cwd](../docs/decisions/2026-06-06-project-root-vs-agent-cwd.md) model without moving the workspace state root or conversation. The auth-free bootstrap `SessionManager` opens history without a live `AgentSession`. It seeds branch projection from the session header cwd. It folds sparse upstream `uix.turn-state` cwd transitions to derive the selected leaf cwd. Main projects self-contained tool items carrying their execution cwd and a normalized `ToolFileLocation` (`absolutePath` plus a cwd-relative-or-absolute `displayPath`). Surfaces observe current cwd through a status snapshot plus change events rather than reconstructing it from transcript deltas. A cwd change is idle-only and becomes durable before any tool executes under it. Then the same session file and leaf reopen with `cwdOverride` and replacement cwd-bound services plus `AgentSession`. This is a same-history runtime rebind, not a UIX feature reload: ordinary Pi reload retains the session and refreshes resources/runtime bindings. Before implementation, settle candidate-creation failure recovery, missing-path fallback, project trust, and status/turn-state restoration ordering.
- **Branchable application persistence with DoltLite**: offer apps built on UIX an optional feature-facing relational persistence store. It provides commit, rollback, branch, diff, and eventual merge semantics under the shared [rollback boundaries](../docs/design/rollback-boundaries.md) model. DoltLite is the leading embedded local implementation candidate because it combines a SQLite-shaped application boundary with Dolt-style version history. Verify Node/Electron bindings, cross-platform packaging, transaction/concurrency behavior, merge/conflict APIs, migration compatibility, licensing, maturity, and a hostable implementation path before promoting this seed. Keep the authorities explicit: Git owns workspace source and `uix.workspace.json`, DoltLite owns application data, and Pi session branches own conversation plus feature turn state. A future workspace checkpoint may coordinate immutable refs from all three without claiming a distributed atomic transaction. Monaco and agent file edits should share the Git checkpoint path described in [pane-and-file-versioning](../docs/design/pane-and-file-versioning.md). Per-Agent worktrees and matching data branches remain future integration capabilities. This persistence seed does not itself implement UIX's later multi-Agent orchestration primitives. The DoltLite store is gitignored from the file layer so the two authorities never double-version the same bytes. Its branches bind to the conversation through the same turn-state pointer model as file checkpoints. See [session worktrees and turn checkpoints](../docs/decisions/2026-08-08-session-worktrees-and-turn-checkpoints.md).
- **Local server CLI and address discovery**: the versioned HTTP catalog, deployment profiles, startup configuration, logging, and signal handling have landed. Remaining local-operations work is a stable CLI JSON projection plus process-address advertisement and stale-advertisement recovery for a future native launcher. Browser opening and writable workspace operations should land only with a current caller rather than as speculative parity work.
- **Independent distribution and release safety**: build Electron and the server as independent artifacts. Package the server as a Node single executable without Electron or implicit app features. Run the release matrix on macOS plus Linux or a container-like environment. Before non-loopback distribution, audit the implemented CSP, CORS, iframe origins, path traversal, cache policy, and production asset layout against the accepted web-host specification. Promote packaging and safety into separate plans if they no longer form one reviewable deliverable.
- **Packaged-binary workspace template**: Create New Workspace scaffolds the repo's bare `templates/workspace/` source. A packaged app needs that template shipped as readable source under `resourcesPath` so its ejected Pi tools remain the worked example for agents authoring features. Lands with the electron-builder/packaging arc, which doesn't exist yet.
- **Session inspector / debug mode**: menu toggle rendering `display: false` custom messages (and other hidden entry streams) in the conversation pane. Renderer-only, the transcript items already include customType/content/details.
- **Transient notices / toast rendering**: provide a substrate channel for backend-originated ephemeral notices. Also provide a frontend invocation path that can feed the same notice model. The producer side should stay simple. The unresolved part is renderer ownership and placement. Options still open: one global renderer, feature-selected renderers (Chat showing agent notices inline), or routing notice types/scopes to different consumers. Also settle whether frontend notices stay local or submit through a channel handler. Settle how duplicate rendering is prevented when multiple consumers exist. Settle which notices target one client versus every attached client. Notices are transient presentation, not session entries or workspace settings.
- **Agent-assisted runtime recovery**, turn captured UIX failures into easy handoff points for the vibe-coding audience rather than requiring DevTools or copied stack traces. Feature activation/reload failures, surface error boundaries, channel/backend failures, and recognized inference-provider errors should produce a structured diagnostic. It carries both a stable searchable error `code` and a unique per-occurrence `diagnosticId`. Mint the id at the first capture boundary and preserve it through propagation. Each layer may append bounded, timestamped context entries relevant to the failure. Those entries cover owner, phase, operation, feature/session/generation/cell identity, validation paths, and safe state refs. They never replace the original cause or dump arbitrary application state. The diagnostic includes a human-safe summary, expandable technical details, cause chain, stack, and relevant runtime/log context, all sanitized of credentials and other secrets. The substrate-owned recovery surface offers dismissal, an optional "What were you doing, and what did you expect?" input, and **Ask agent to fix**. The human explanation becomes an ordinary visible message. The complete sanitized diagnostic rides as hidden model-visible context, giving the agent an edit → reload/test → verify loop without cluttering the transcript. Do not auto-run by default. If inference itself is unavailable, the human must first select a working model. Recovery can then fork from the failed branch and ask that model to diagnose the original provider/configuration failure. Keep this a diagnostic handoff, not an agent-side UI mutation API: the agent repairs files or the owning source of truth.
- **Cmd+R routes through substrate reload:** rebase onto [`feature-composition.md`](../docs/specs/feature-composition.md). The action first requests selected-Agent composition replacement. Successful acceptance then reloads affected workspace pages, while rejected preparation preserves the previous pages. A page reload is not itself a backend reload request. Audit existing keybinding and host actions before selecting this work.
- **Opt-in agent-initiated workspace reload**: let workspace configuration gate whether the runtime registers and advertises an agent-callable reload capability. The intended edit/install/reload loop lets the agent update feature source or dependencies. It runs the package install explicitly. It requests the existing substrate reload without waiting for a human action. Dependency installation does not become an automatic reload phase. Because the calling tool belongs to the runtime being replaced, it schedules reload only after the agent settles. It never disposes its own active tool/extension context. Before implementation, settle run termination, queued reload coalescing, feature-state commit, and failed-reload reporting/recovery. Also settle how prominently the workspace communicates that enabling the capability lets agent-edited trusted main-process feature code activate without another confirmation.
- **Replace `ReservedFeatureIds` with registration-order collisions**: enforce substrate claims by actually registering the claimed thing first. The substrate registers before features, and registries throw on duplicates. Do not rely on a hand-maintained list that can drift. Workspace settings scopes already work this way (namespaces hydrate at startup: `WorkspaceSettingsStore` throws on duplicate scope ids). Migrate `agent` by having the channel registry rely on the substrate's own prior registration colliding naturally. `uix` is the hard case. It's a _prefix_ claim on session entry types (`uix.turn-state`), with no registered object to collide with. It needs an explicit prefix-claim mechanism or stays listed. The list shrinks as claims migrate. Delete it when only registrable claims remain.
- **Live agent message taps**, add a feature-facing, read-only contribution for reacting to messages/turns only as they occur. The current renderer agent feed and substrate-internal Pi installers are not that backend feature API. Taps never rerun during session restoration. A tap may update feature working state. Anything that must survive reload, session switch, restart, or branch rewind must reach `uix.turn-state`. That happens inline or through stable referenced ids at an appropriate lifecycle boundary. Uncommitted buffer state is intentionally ephemeral. Restoration consumes feature-scoped turn-state history instead of regexing historical messages, which avoids replaying side effects and remains valid after compaction. Settle finalized-versus-persisted event timing, ordering relative to turn-state preparation, and the minimal typed event vocabulary before promotion.
- **Multi-Agent orchestration primitives**: let UIX coherently manage state among Agents, subagents, humans, and application code while Pi executes each individual loop. Each Agent receives its own branch-scoped viewpoint across conversation, feature turn state, managed documents, filesystem worktree, and future branchable application data. UIX owns Agent topology and lifetime, durable Agent-to-Agent messaging, explicit read-only artifact sharing, human visibility, and coordination of state references across authorities. Applications and features choose domain roles, routing, merge policy, and workflow rather than rebuilding orchestration mechanics. Before promotion, settle Agent and branch identity, parent/subagent lifecycle, message persistence, causality, and artifact grants. Also settle revocation, checkpoint coordination, and promotion or merge behavior.
- **Scheduled and recurring Agent turns**: define the UIX-specific scope without duplicating host or system cron. Decide whether a schedule creates a durable session, resumes a named session or branch, or inserts a message into an existing session. Generic recurring jobs should use host cron. UIX likely earns scheduling only when Agent-session identity, transcript visibility, runtime lifetime, or missed/concurrent-run policy matter.
- **Session triggers and inspectable background agents**: let features react to completed session entries by starting restricted one-shot agents on background branches. The first use case can name a session after its third durable user message. Each branch starts with a marker that records its purpose, visibility, and trigger. Normal views hide these branches, while a debug view can show their activity. The session coordinator creates the branch and prevents duplicate or recursive triggers. Host-authored retention keeps the agent alive for its run. The agent receives only target-bound tools, and a human title change wins over a late automation result. This capability uses durable session and branch identity instead of public agent-instance identity.
- **User-action event log on CustomEntry**: append-only `pi.appendEntry` streams folded by D3 reducers. Model-invisible, branch-aware, no second database. Keep low-frequency (whole session file loads into memory). Leaf discipline unresolved for concurrent writers.
- **Fan-out one-off mode**, prepared root per app variant (system prompt + tool contracts + vocabulary + seeded state entries), fork per invocation, never rejoins. Sibling branches make every run inspectable and identical prefixes align with provider prompt caching. Needs lifecycle design (fork-per-invocation creation/disposal, concurrency), not new messaging. Execution-VM forks from prepared goldens are the likely mechanism once the execution boundary exists, see [agent isolation and the execution boundary](../docs/design/agent-isolation-and-execution-boundary.md).
- **How-to placement and examples**: decide the final home for the user-implementation guides. Colocating with the API boundary is the leading candidate. Then seed `examples/` as primitives land.
- **Documentation framework gaps**: define the compass test, kind-migration rules, the commit-time loop protocol, and budget tests. The compass test classifies new and moved documents: action or cognition, then acquisition or application. Kind-migration rules cover reference traffic spawning a how-to, repeated comments becoming conventions, and decisions graduating to creed. The commit-time loop protocol captures, distills residue, regenerates indexes, scans backports, and verifies. Budget tests cover creed admission and always-loaded root size discipline. These were the deferred framework work beside the landed code-proximate migration.
